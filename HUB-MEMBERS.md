# Automatic group participants: Hub integration

The Bouncer client is ready for this contract. At inspection on 17 October 2026,
Chat-Hackers/tool-hub's `src/webserver.ts` had `/api/room` (message history),
but no full member roster endpoint. This feature requires a Hub change.
Message history must not be treated as a complete current membership list.

## 1. Configure Bouncer

Set `HUB_URL=https://dev.dashboard.chathackers.uk` in Vercel Production and redeploy.
Use the actual Hub origin if different. The registration JSON and database schema
stay the same. Keep `MODULE_SECRET` unchanged and register/activate the module in
the configured room. Upload the approved list, then click **Sync group members**.

## 2. Add a protected Hub endpoint

Implement `GET /api/members?roomId=...&toolId=whatsapp-bouncer`.
The Bouncer sends `Authorization: Bearer <registered module.secret>`.
The Hub must validate that secret against the tool registration and confirm the
tool is active in the requested room before returning anything. Return 401/403
for denied requests. Do not include the secret in URLs or logs.

Get the full current joined member state from the Hub's authenticated Matrix
client (for example the Matrix `/rooms/{roomId}/members?membership=join` API).
Resolve phone numbers through the WhatsApp bridge's trusted contact mapping.
Check the deployed bridge's actual supported identity lookup; if the bridge
cannot resolve an opaque/LID identity, return null. A display name is not proof
of a phone number. Only decode a numeric ghost ID if the bridge's configured
identity format is documented and verified for that deployment.

Return JSON:

```json
{
  "roomId": "!example:matrix.example",
  "complete": true,
  "observedAt": "2026-10-17T14:00:00.000Z",
  "members": [
    {
      "userId": "@bridge_identity:matrix.example",
      "name": "Example member",
      "phoneNumber": "+447700900101",
      "phoneSource": "bridge"
    },
    {
      "userId": "@opaque_identity:matrix.example",
      "name": "Number unavailable",
      "phoneNumber": null,
      "phoneSource": "unavailable"
    }
  ]
}
```

`observedAt` is the time roster retrieval **started**, before fetching any pages
or resolving contacts. Return `complete: true` only after all joined members are
retrieved. On upstream errors or truncation return an error, not an empty success.
Maximum 5,000 members and 1.5 MB JSON. Include bots/Matrix-only identities with
null numbers; organisers can explicitly exclude service accounts in Bouncer.
Only set `phoneSource: "bridge"` for trusted bridge mappings. Bouncer normalises
numbers, flags duplicates/missing values, and marks absent members as left only
after a complete snapshot. Newer join/leave observations take precedence.

## 3. Enrich ongoing membership webhooks

Keep forwarding the existing `event`, `botUserId`, and `displayName` fields.
For `m.room.member`, resolve the **target `event.state_key`**, not `event.sender`.
Add a separate top-level field generated by the Hub:

```json
{
  "event": {
    "type": "m.room.member",
    "room_id": "!example:matrix.example",
    "state_key": "@bridge_identity:matrix.example",
    "sender": "@admin:matrix.example",
    "event_id": "$example-join",
    "origin_server_ts": 1792245600000,
    "content": { "membership": "join", "displayname": "Example member" }
  },
  "participant": {
    "userId": "@bridge_identity:matrix.example",
    "phoneNumber": "+447700900101",
    "phoneSource": "bridge"
  }
}
```

Generate this enrichment from the trusted bridge lookup, not arbitrary fields in
`event.content` or message text. Unknown numbers may be sent as null. Omitting
`participant` keeps the existing mapping and supports the original Hub webhook.
The userId must equal state_key. The existing webhook secret protects this request.

## Verification with a consenting test group

* Confirm unauthenticated/wrong-secret/inactive-room roster requests are denied.
* Sync a full roster: one approved, one unmatched, one unavailable number.
* Confirm numbers come from the bridge; number-like display names cannot supply them.
* Join and leave during a sync: newer membership events must win.
* Repeat a membership event: no duplicate participant is created.
* Return a partial/failed roster: existing participants must remain unchanged.
* Check a changed number invalidates the previous organiser decision.

This integration compares members and records review decisions; it does not kick,
ban, or send group messages. Validate the bridge lookup and live Hub end to end
before claiming automatic number discovery works.
